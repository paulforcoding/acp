# acp 与原生 cp 的功能对比

> 本报告对比 acp（async cp / agent cp）与 macOS 自带 cp、GNU cp 的实际复制能力，帮助用户理解 acp 能做什么、不能做什么。

---

## 1. 覆盖行为

| 场景 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **目标存在且可写** | 直接覆盖，不做任何提示 | 直接覆盖，不做任何提示 | 直接覆盖，不做任何提示 |
| **目标存在且不可写（如只读文件）** | **报错退出** | 报错退出 | 报错退出 |
| **强制覆盖不可写目标** | 不支持。不可写目标永远报错，不会自动删除重试 | 支持（`-f`） | 支持（`-f`/`--force`） |
| **交互式提示** | 不支持（Agent 场景不需要 stdin 交互） | 支持（`-i`） | 支持（`-i`） |
| **跳过已存在目标** | 不支持 | 支持（`-n`） | 支持（`-n`/`--no-clobber`） |
| **仅当源更新时才覆盖** | **CksumCopy 模式下支持**：源与目标 size+mtime 完全相同时跳过整文件 | 不支持 | 支持（`-u`/`--update`） |
| **备份旧目标** | 不支持 | 不支持 | 支持（`--backup`） |
| **删除后再复制** | 不支持 | 不支持 | 支持（`--remove-destination`） |

**用户需知：**
- acp 对可写目标的默认行为与 cp 一致：直接覆盖，不提示。
- 差异在于 acp **没有 `-f` 的删除重试机制**，复制到只读目标时会直接失败。
- acp **没有交互式提示**，这是 Agent-First 定位的设计选择（Agent 无法回答终端提问）。
- 如果需要"只复制有变化的文件"，请使用 acp 的 **CksumCopy 模式**。

---

## 2. 递归与目录复制

| 功能 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **递归复制目录** | **自动递归**，源为目录时自动复制整棵树 | 需显式加 `-R` 或 `-r` | 需显式加 `-R` 或 `-r` |
| **目录复制自身检测** | 支持 | 支持 | 支持 |
| **源=目标检测** | 支持 | 支持 | 支持 |
| **多源复制到目录** | 支持 | 支持 | 支持 |
| **保留源目录层级** | 不支持 | 不支持 | 支持（`--parents`） |
| **非目标目录模式** | 不支持 | 不支持 | 支持（`-T`） |

**用户需知：**
- acp 复制目录**不需要 `-R`**，这是为了方便 Agent 调用（少一个参数少一个出错点）。
- 如果你需要"把 `src/a/b/file` 复制到 `dst/src/a/b/file`"（保留完整路径层级），acp 不支持，GNU cp 的 `--parents` 可以做到。

---

## 3. 支持的文件类型

| 文件类型 | acp | macOS cp | GNU cp |
|----------|:---:|:---:|:---:|
| 普通文件 | ✅ | ✅ | ✅ |
| 目录 | ✅ | ✅ | ✅ |
| 符号链接 | ✅ | ✅ | ✅ |
| FIFO（命名管道） | ❌ 跳过 | ✅（`-R` 时） | ✅ |
| 块设备文件 | ❌ 跳过 | ✅（`-R` 时） | ✅ |
| 字符设备文件 | ❌ 跳过 | ✅（`-R` 时） | ✅ |
| Socket | ❌ 跳过 | ❌ 跳过并警告 | ✅ |

**用户需知：**
- acp **仅支持普通文件、目录、符号链接**三类。这是项目明确的设计定位。
- 如果你用 acp 递归复制一个包含设备文件或 FIFO 的目录树（如 `/dev` 或某些系统目录），这些文件会被**静默跳过**。
- 日常文件复制场景（文档、代码、数据）不受影响。

---

## 4. 元数据保留能力

| 元数据 | acp | macOS cp | GNU cp |
|--------|:---:|:---:|:---:|
| 文件权限（mode） | ✅ 能保留 | ✅ 能保留（`-p`） | ✅ 能保留（`-p`） |
| 属主（uid/gid） | ✅ 能保留 | ✅ 能保留（`-p`） | ✅ 能保留（`-p`） |
| 时间戳（atime/mtime） | ✅ 能保留 | ✅ 能保留（`-p`） | ✅ 能保留（`-p`） |
| 扩展属性（xattr） | ✅ 能保留 | ✅ 能保留（`-p`） | ✅ 能保留（`-p`） |
| ACL | ✅ 能保留 | ✅ 能保留（`-p`） | ✅ 能保留（`-p`） |
| 稀疏文件空洞 | ✅ 能保留 | ✅ 能保留 | ✅ 能保留 |
| 同步落盘（fsync） | ✅ 能保留 | ❌ 不能 | ❌ 不能 |
| SELinux 安全上下文 | ❌ 不能 | ❌ 不能 | ✅ 能保留 |
| BSD 文件 flags（macOS 特有） | ❌ 不能 | ✅ 能保留（`-p`） | ❌ 不能 |
| 源内硬链接关系 | ❌ 不能 | ❌ 不能 | ✅ 能保留（`--preserve=links`） |

**用户需知：**
- **acp 默认就保留所有核心元数据**（权限、属主、时间戳、扩展属性、ACL），无需额外参数。
- macOS cp 和 GNU cp **默认不保留元数据**，需要加 `-p` 或 `-a`。
- acp 独有的 `SyncWrites` 功能确保每个文件复制完成后都执行 fsync 落盘，适合对数据完整性要求高的场景。
- acp 不支持 GNU cp 的 `--preserve=links`（保留源内硬链接关系），相同 inode 会被复制为独立文件。

---

## 5. 稀疏文件处理

| 功能 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **默认行为** | 检测并保留稀疏空洞 | 保留稀疏空洞 | 启发式检测并保留 |
| **禁用稀疏保留** | `--disable-sparse` | `-S` | `--sparse=never` |
| **强制创建稀疏文件** | 不支持 | 不支持 | 支持（`--sparse=always`） |
| **内核 extent 扫描（FIEMAP）** | 不支持 | 不支持 | 支持 |

**用户需知：**
- 三者默认都能处理稀疏文件，日常使用无需担心。
- GNU cp 的稀疏处理最精细（支持 FIEMAP 和强制稀疏模式），acp 和 macOS cp 都是"透明保留"方案。

---

## 6. 符号链接处理

| 行为 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **默认行为** | **始终复制为符号链接**（不跟随） | `-R` 时默认不跟随，非 `-R` 时默认跟随 | `-R` 时默认不跟随，非递归默认跟随 |
| **始终不跟随** | ✅（唯一模式） | ✅（`-P`） | ✅（`-P`） |
| **始终跟随** | ❌ 不支持 | ✅（`-L`） | ✅（`-L`） |
| **仅命令行参数跟随** | ❌ 不支持 | ✅（`-H`） | ✅（`-H`） |
| **悬空符号链接** | ✅ 支持 | ✅ 支持 | ✅ 支持 |

**用户需知：**
- acp **始终复制符号链接本身**，永远不会去复制链接指向的实际文件。
- 如果你需要"复制软链接指向的实际文件内容"，需要先用 `readlink` 或 `find` 预处理，不能直接用 acp。
- 这个设计简化了实现，避免了循环链接和竞态条件风险。

---

## 7. 硬链接

| 功能 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **创建硬链接代替复制** | 不支持 | 支持（`-l`） | 支持（`-l`） |
| **创建符号链接代替复制** | 不支持 | 支持（`-s`） | 支持（`-s`） |
| **保留源内硬链接关系** | 不支持 | 不支持 | 支持（`--preserve=links`） |

**用户需知：**
- acp 每次复制都是独立的新文件，不会创建硬链接。
- 如果你有一个大目录树，其中多个文件是同一 inode 的硬链接，acp 会复制成多个独立的文件（占用多份空间），GNU cp 的 `--preserve=links` 可以保留硬链接关系。

---

## 8. 校验和与差异复制（acp 独有）

| 功能 | acp | macOS cp | GNU cp |
|------|:---:|:---:|:---:|
| **校验和复制（仅写差异块）** | ✅ `CksumCopy` 模式 | ❌ | ❌ |
| **校验和校验（仅比对不写入）** | ✅ `CksumOnly` 模式 | ❌ | ❌ |
| **支持算法** | xxhash64 / MD5 / SHA-256 | — | — |
| **rsync 式优化** | ✅ size+mtime 匹配则跳过整文件 | ❌ | ❌ |
| **元数据比对** | ✅ `CksumOnly` 比对权限/属主/时间戳/xattr/ACL | ❌ | ❌ |

**用户需知：**
- 校验和复制/校验是 **acp 的核心差异化功能**，两个原生 cp 完全不支持。
- **CksumCopy**：适合"上次复制过，现在源有少量更新"的场景——acp 只复制真正变化的数据块。
- **CksumOnly**：适合"检查两份拷贝是否一致"的审计场景——输出详细的 mismatch 日志，不修改目标。
- size+mtime 快速跳过：如果源和目标文件大小和修改时间完全一致，acp 会直接跳过 block-level 校验，大幅提升性能。

---

## 9. CoW / 写时复制

| 功能 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **APFS clonefile** | 不支持 | 支持（`-c`） | 不支持 |
| **Linux reflone（FICLONE）** | 不支持 | 不支持 | 支持（`--reflink`） |

**用户需知：**
- CoW（写时复制）能在支持的文件系统上实现**零拷贝**复制（瞬间完成、不占用额外空间）。
- acp 不支持 CoW。在 APFS 上 macOS cp `-c` 可以实现；在 Btrfs/XFS 上 GNU cp `--reflink` 可以实现。

---

## 10. 跨文件系统限制

| 功能 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **不跨文件系统** | 不支持 | 支持（`-x`） | 支持（`-x`） |

**用户需知：**
- acp 没有 `-x` 等价功能。递归复制大目录时，如果目录下挂载了其他文件系统（如 `/home/user/mnt`），acp 会一并复制进去。
- 如果你需要限制在单个文件系统内，需要手动排除挂载点。

---

## 11. 持续同步（acp 独有）

| 功能 | acp | macOS cp | GNU cp |
|------|:---:|:---:|:---:|
| **监控源目录变化并自动同步** | ✅ `inotify`（Linux）/ `FSEvents`（macOS） | ❌ | ❌ |
| **事件去重** | ✅ | — | — |
| **监控范围** | 递归监控所有子目录 | — | — |

**用户需知：**
- acp 的 `--enable-inotify` 可以持续监控源目录，检测到文件变化后自动复制到目标。
- 启用后主循环**永不退出**，适合"保持两个目录同步"的场景。
- 这是两个原生 cp 完全没有的能力。

---

## 12. 并发与异步 I/O（acp 独有）

| 功能 | acp | macOS cp | GNU cp |
|------|:---:|:---:|:---:|
| **异步 I/O** | ✅ libaio / io_uring / GCD | ❌ 同步 | ❌ 同步 |
| **并发线程** | ✅ `--parallelism` 可调 | ❌ 单线程 | ❌ 单线程 |
| **I/O 队列深度** | ✅ `--queue-depth` | ❌ | ❌ |
| **批量 I/O 提交** | ✅ `--batch` | ❌ | ❌ |
| **Direct I/O（绕过页缓存）** | ✅ `--enable-direct-io` | ❌ | ❌ |
| **I/O 看门狗（卡住检测）** | ✅ `--io-stuck-timeout` | ❌ | ❌ |

**用户需知：**
- acp 使用异步 I/O（Linux 用 io_uring/libaio，macOS 用 GCD），配合多线程并发，在大文件和高队列深度下性能显著优于同步 cp。
- Direct I/O 适合复制极大大文件时避免污染系统页缓存。
- I/O 看门狗可以检测并报告长时间未完成的 I/O 操作。

---

## 13. 日志与观测性（acp 独有）

| 功能 | acp | macOS cp | GNU cp |
|------|:---:|:---:|:---:|
| **结构化 NDJSON 日志** | ✅ 每个文件独立事件 | ❌ | ❌ |
| **文件级事件** | ✅ file_start / file_complete / file_error 等 | ❌ | ❌ |
| **进度摘要（含 ETA）** | ✅ progress_summary | ❌ | ❌ |
| **状态快照文件** | ✅ state_snapshot | ❌ | ❌ |
| **终端逐文件输出** | ❌ 无 `-v` 等价功能 | ✅ `-v` | ✅ `-v` |
| **SIGINFO (^T) 进度** | ❌ | ✅（macOS 特有） | ❌ |

**用户需知：**
- acp 没有终端逐文件输出（`-v`），取而代之的是**机器可读的结构化日志**（NDJSON 格式）。
- 这是为 Agent 场景设计的：Agent 可以解析 JSON 事件来跟踪复制进度、检测错误、计算 ETA，而不需要解析人类可读的终端输出。

## 14. 安全与竞态条件

| 功能 | acp | macOS cp | GNU cp |
|------|-----|----------|--------|
| **源=目标检测** | ✅ | ✅ | ✅ |
| **目录复制自身检测** | ✅ | ✅ | ✅ |
| **目标竞态条件防护** | 有限 | 有限 | 较完善（`O_EXCL` / 哈希表） |
| **复制时临时限制权限** | 不支持 | 不支持 | 支持 |
| **防止逃逸目标目录** | 不支持 | 支持（`O_RESOLVE_BENEATH`） | 不支持 |

## 15. 总结

### acp 适合什么场景

1. **Agent 驱动的文件复制** — 结构化日志让 Agent 能感知和推理复制状态
2. **大规模数据迁移** — 异步 I/O + 并发线程 + Direct I/O，高效处理大文件和海量小文件
3. **增量同步** — CksumCopy 只写差异块，CksumOnly 只比对不写入
4. **持续同步** — inotify/FSEvents 监控源目录变化，自动同步
5. **数据完整性要求高** — 默认 fsync 落盘，默认保留所有元数据

### acp 不适合什么场景

| 场景 | 原因 | 替代方案 |
|------|------|----------|
| 复制包含设备文件/FIFO 的系统目录 | acp 只支持三类文件 | 用原生 `cp -R` |
| 需要交互式确认覆盖 | acp 无 stdin 交互 | 用原生 `cp -i` |
| 需要强制覆盖只读目标 | acp 对不可写目标报错退出 | 用原生 `cp -f`，或先 `chmod +w` |
| 需要保留源内硬链接关系 | acp 不支持 | 用 GNU `cp --preserve=links` |
| 需要跟随符号链接复制实际文件 | acp 始终复制链接本身 | 先用 `find`/`rsync` 预处理 |
| 需要 CoW 零拷贝（APFS/Btrfs） | acp 不支持 clonefile/reflone | 用 `cp -c`（macOS）或 `cp --reflink`（Linux） |
| 需要限制在单个文件系统内 | acp 无 `-x` | 用原生 `cp -x` |

### 核心定位差异

- **cp** 是通用命令行工具，功能全面、参数丰富，面向人类交互。
- **acp** 是 Agent-First 的专用复制工具，默认行为针对 Agent 场景优化（自动递归、默认归档、结构化日志、异步高性能），牺牲了部分通用性（无交互、不跟随链接、不支持特殊文件）。
